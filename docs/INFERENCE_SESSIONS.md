# 추론 세션과 체결 확인 계약

`/optimize`는 주문을 보내지 않는 제안 API입니다. 목표 비중을 실제 체결로 저장하지 않습니다.

## 세션

1. `POST /inference-sessions`로 서버가 발급한 `session_token`을 받습니다.
2. 클라이언트별로 토큰을 보관하고 `/optimize` 요청 본문에 전달합니다.
3. 같은 투자 에피소드에는 같은 토큰과 `state.episode_id`를 사용합니다.
4. 신규 RecurrentPPO 투자 에피소드는 명시적인 현금 상태와 `reset_episode: true`로 시작합니다.
5. 연속 요청은 실제 보유 상태와 다음 거래일 데이터를 전달합니다. 같은 관측 재시도는 캐시를 사용합니다.

토큰 없이 `/optimize`를 호출하면 새로운 세션을 발급하고 응답에 토큰을 반환합니다. 서로 식별되지 않은 요청을 기존 에피소드에 합치지 않습니다. 첫 요청의 응답 유실까지 재시도해야 한다면 먼저 세션을 발급받으세요.

토큰은 임의로 지정하는 사용자 ID가 아니라 서버 발급 bearer capability입니다. 토큰 소유자가 세션에 접근하므로 다른 사용자에게 공유하지 않습니다. 현재 앱에는 사용자 인증이 없으며 인증된 사용자 신원을 증명하는 기능은 아닙니다. 서버에는 토큰의 SHA-256만 저장합니다. 배포 시 HTTPS를 사용하세요.

상태 없는 현금 조회는 별도의 preview 공간을 사용합니다. 투자 에피소드의 clock, LSTM, 안전장치, 실행 기준을 덮어쓰지 않습니다. 대시보드는 Streamlit 사용자 세션에 토큰을 보관합니다.

토큰과 상태는 모델별 기존 service_state 파일에 함께 저장하며 서버 재시작 시 복원합니다. 모델이 변경되면 기존 모델 해시 검증을 유지합니다. HTTP에 소유자가 없었던 이전 캐시를 새 토큰에 자동 귀속시키지는 않습니다. 이전 활성 에피소드는 기존 프로세스 내부 호출에서만 유지하며, HTTP 클라이언트는 새 세션을 명시적으로 시작해야 합니다. 직접 Python 호출에서 토큰 생략은 기존 단일 소유자 로컬 인터페이스와의 호환 목적이며 다중 사용자 서버에서는 반드시 토큰을 전달해야 합니다.

## 실제 체결 확인

확인되지 않은 `state.last_executed_weights`는 그 요청의 입력일 뿐 저장된 실행 기준을 바꾸지 않습니다. 실제 체결을 확인했을 때만 다음 객체를 요청에 추가합니다.

```json
{
  "execution_confirmation": {
    "execution_id": "broker-fill-123",
    "date": "2026-11-19",
    "weights": {"SPY": 0.3, "QQQ": 0.2}
  }
}
```

예시는 두 자산 환경입니다. 실제로는 모델의 모든 자산을 포함하고 미보유 자산은 0이어야 합니다. 확인 날짜와 비중은 같은 요청의 실제 `state.date`, `state.weights`와 일치해야 합니다. 과거 기준을 등록하려면 체결 시점의 상태로 확인한 후 이후 거래일의 실제 상태를 전달합니다. 과거 확인보다 오래된 날짜나 동일 체결 ID에 다른 내용을 보내는 요청은 거부합니다. 이 확인은 호출자의 체결 확인이며 브로커 연동 검증은 아닙니다.

확인 없이 모델 제안만 받은 경우 기존 실행 기준을 보존합니다. 검증이나 저장 실패 시 메모리의 에피소드 상태도 되돌립니다.

## 모델·결과 호환성

관측/action 차원, LSTM 구조, 모델 파일 형식은 바뀌지 않습니다. 기존 모델을 다시 학습하지 않고 로드할 수 있습니다. Baseline 부분 청산의 신규 진입 및 Legacy 경계 비중 오류를 바로잡았으므로 해당 사례의 평가 결과는 달라질 수 있습니다. 비교 시 기존 결과를 새 코드로 다시 평가하세요.

이전 거래 기록에 `holdings_count`가 없으면 `held_*`에서 계산하고, 계산할 수 없으면 holdings 통계는 JSON `null`(unavailable)을 반환합니다. 기존 recurrent cache의 실행 기준 누락은 검증된 요청 상태로 보완하며 LSTM을 다시 실행하지 않습니다.


## 실행 ID 이력과 재시도

`execution_id`는 호출자가 전달합니다. 현재 추천 화면은 `execution_confirmation`을 전달하지 않으며, 백테스트의 가상 거래도 이 API를 호출하지 않습니다. 추천 요청은 체결 확인이나 ID를 자동 생성하지 않습니다.

승인된 확인 내용과 당시 응답은 세션·에피소드별 `execution_history`에 저장합니다. 같은 ID의 내용 변경(비중 또는 날짜)은 최신 기록인지와 관계없이 거부합니다. 새로운 ID의 확인에는 기존 날짜 순서 검증을 적용합니다.

이미 처리한 과거 ID의 동일한 재전송은 확인 당시의 저장 응답을 반환하고, 현재 실행 기준·clock·LSTM을 변경하지 않습니다. 이 응답은 과거 확인의 재시도 결과이며 새로운 추천이 아닙니다. 현재 추천을 받으려면 최신 실제 상태를 `execution_confirmation` 없이 전달하세요.

구버전 저장 파일은 마지막 확인 1건만 이력으로 이관할 수 있습니다. 구버전이 이미 덮어써서 잃어버린 더 오래된 ID는 복구할 수 없습니다. 이관한 기록에 원래 응답이 없고 이후 확인이 승인된 경우, 과거 동일 확인 재시도는 최신 저장 응답을 반환하며 상태를 되돌리지 않습니다. 명시적인 현금 reset으로 새 에피소드를 시작하면 해당 에피소드의 기준과 이력은 함께 초기화합니다.

계속되는 에피소드는 현재 보유가 모두 현금이어도 저장된 마지막 실행 기준을 우선 복원합니다. 신규 현금 미리보기·명시적 reset에는 0을 사용하고, 기록이 없는 현금 상태에만 0 fallback을 사용합니다.

## 세션 보관 한도와 만료

- `INVESTMENT_AI_MAX_SESSIONS`: 모델 실행별 최대 세션 수, 기본 `256`.
- `INVESTMENT_AI_SESSION_TTL_SECONDS`: 발급 후 유효 시간(초), 기본 `86400`(24시간). 사용해도 만료 시각은 연장되지 않습니다. 장기간 연속 추론이 필요하면 운영 기간에 맞게 설정하세요.
- 두 값은 양수여야 합니다. 명시적 `/inference-sessions`와 토큰 없는 `/optimize`에 동일한 한도를 적용합니다.
- 한도에 도달하면 `429`를 반환하며 유효한 다른 세션을 밀어내지 않습니다. 기존 유효 토큰 요청은 계속 사용할 수 있습니다.
- 만료 시각은 영속화하며 같은 실행의 서버 재시작으로 연장되지 않습니다. 만료 토큰은 기존 unknown-session `422`로 거부하여 화면이 토큰을 초기화할 수 있습니다.
- 만료된 세션의 clock, LSTM, 안전장치, 실행 기준 및 확인 이력은 다음 접근 또는 서버 시작 시 함께 정리합니다. 만료된 에피소드는 계속 추론할 수 없고 새 세션·에피소드가 필요합니다.
- 만료 정보가 없는 구버전 토큰은 최초 업그레이드 시 유효 시간을 한 번 부여해 저장합니다. 이미 한도를 초과한 구버전 레지스트리는 유효 세션을 임의 삭제하지 않고 새 발급을 제한하며 만료 시 정리합니다.
- 토큰 없는 추천 요청은 임시 세션을 사용하고 성공했을 때만 저장합니다. 검증 실패나 저장 실패로 호출자가 받지 못한 토큰을 남기지 않습니다.

## 같은 날 추천 후 체결 확인

같은 관측값으로 오늘의 추천을 이미 계산한 경우, 새로운 체결 확인이 바꾸는 실행 기준 비중은 모델 입력이 아닙니다. 저장된 실제 raw 목표 비중을 사용해 거리·리밸런싱 사유·최종 제안만 다시 계산하고 LSTM은 진행시키지 않습니다. 동일 확인 재전송은 승인된 응답을 반환합니다.

시장 데이터·현재 보유 비중·포트폴리오 상태 등 모델 관측값까지 바뀐 동일 날짜 요청은 이 경로로 재사용하지 않으며 기존 순서 검증을 유지합니다. Baseline과 Legacy 모두 같은 날 확인을 지원합니다. 추천은 체결 확인을 자동 생성하지 않고, 실제 주문도 전송하지 않습니다.
